## Stage A feasibility: schema while old behavior remains live

**Not established.** Replit's [production database documentation](https://docs.replit.com/features/data-and-storage/development-and-production) says development schema changes are applied to production *at publishing*; its [publishing documentation](https://docs.replit.com/features/publishing/after-you-publish) says a new built version is prepared alongside the current one and promoted at the same URL. Neither cited page documents a schema-only Publish control, independently pinning an old API/worker revision while applying the current managed diff, or migration-completion-before-run ordering for this artifact.

- Publishing **current main** is **not Stage A**. It would deploy the new API, worker parent, red-zone route and UI along with the schema diff. If the parent runs before the diff and Publish does not retry it, it fails closed and the new deployment may stay unhealthy. If it runs after the diff, Stage B functionality is already enabled, violating Stage A's old-behavior requirement.
- Re-publishing **the old Git revision** is not a verified schema-only option. The platform has not shown a means to select that revision separately from the development schema used by Publish. An ordinary old-code publication is also a worker/code deployment. Checking out or reverting source could cause the development post-merge schema process to reconcile away new tables; do not try that as an improvised migration technique.
- A **compatibility-code release** that deliberately keeps old API/worker/consumer behavior while carrying the additive schema source might be technically possible as a separate, tested code change. It is not prepared or verified here, is **not** schema-only, still has an old/new worker handover, and requires proof of its Publish diff and unchanged behavior. No app-owned production SQL, deploy-build `db:push`, or startup DDL is permitted for this managed database.

The existing old app does not require red-zone tables, so *if* a separately supported schema-only or validated compatibility publication applied the five additive statements, the old API could in principle continue serving during migration. That conditional compatibility is **not proof** of a supported or recoverable Stage A.

## Preview and recovery checkpoint

The same [database documentation](https://docs.replit.com/features/data-and-storage/development-and-production#test-changes-with-a-deployment-preview) describes a deployment preview as a temporary, isolated copy of production for testing schema changes and app updates. It does **not** specify in the cited page how to provision a preview for this artifact, how its database is cloned or identified, or how to promote its result as a separate live schema-only step. No preview or temporary production branch was created. The previous Gate 4 experiment applied the current additive statements in a rolled-back **development** schema; it validated the application gate but not Replit's live Publish ordering or a production database branch.

Replit's [data recovery documentation](https://docs.replit.com/features/data-and-storage/data-recovery) documents production point-in-time restore (Core up to seven days; Pro/Enterprise up to 28 days, with a seven-day default) and optional scheduled backups with one daily restore point. It explicitly states that **app rollback does not restore the database**. We cannot see an independently verifiable, currently restorable production point or an isolated restore from the read-only replica. **No backup was prepared or restore point verified.** Before any Stage A approval, the owner must inspect the **production Database → Settings** recovery/retention controls, record a restore timestamp preceding the release, and confirm a supported restore/test route and retention long enough for both approval windows. If a separate validated backup or isolated restore is required by the owner, arrange it through a documented platform-supported method before release; do not treat a Git checkpoint as that backup.

## Worker, provider, and Phase 6.1 risk

The publishing guide's “prepare alongside” language does not establish when an old VM worker stops relative to the new one starting. Each production parent starts a worker; the code has **no global worker-process singleton**. Database job-row leases and per-feed advisory locks normally exclude duplicate claims of the *same job/feed*, but permit different due jobs to run concurrently and do not rule out expired leases or a brief dual-worker period. The feed scheduler attempts a tick immediately on worker startup. Therefore **zero overlapping provider activity cannot be guaranteed from code or current logs**. Do not separately launch another production worker or infer worker uniqueness from a momentary zero-held-leases query.

The baseline of 259 snapshots, including one official and one frozen, is present now. A code deployment must not alter the approved Phase 6.1 artifact/snapshot identities; compare fixed keys, artifact checksums and row contents before and after each separately approved stage, not only totals. Development Week 2 fact recovery was not copied to production. Any Week 2 production refresh requires its **own authorization**, then source/fact reconciliation; it is not part of Stage A or an automatic proof of Stage B.

## Specific limitation and exact owner actions

The missing platform proof is **a supported, owner-controlled way to apply this managed schema diff while keeping the old app/worker behavior active**, plus a verifiable recovery point and a safe old/new worker handover. Documentation confirms the managed diff is tied to Publish, but does not establish that split. Neither the app's read-only startup gate nor an isolated development transaction supplies it.

1. **Do not approve Stage A yet.** Obtain deployment-specific Replit confirmation or a documented control for a schema-only Publish **or** authorize design/review of a compatibility-code release. Confirm exactly which code revision and database schema snapshot Publish uses, and whether the old/new VM workers can overlap. Do not use direct production DDL, an automatic migration hook, a database-binding swap, or a direct worker workflow.
2. In the production Database recovery controls, verify and record an actual restorable point **before** the first Stage A approval, its retention window, and a supported recovery procedure that does not silently overwrite newer good data. If a preview is offered, verify it has a **separate disposable database identity** and no connection to live production **before** using it; test migration, API readiness and worker-start ordering there only with separate owner authorization.
3. If and only if Stage A becomes supported and independently reviewed, require **separate explicit owner approval** for Stage A. At approval, review the interactive diff for exactly two additive tables/three indexes (including six checks), no drops/truncations/renames or data overwrite, and confirm the old user-visible/API/worker behavior is retained. Do not start the worker separately. Afterward verify the production database identity via live build evidence, two tables, six validated constraints, three ready/valid indexes, baseline data/content, old API health, one logical scheduler owner and no unexplained provider starts. If any check fails, stop; do not treat an app rollback as DB restoration.
4. Require a **second explicit owner approval** for Stage B only after Stage A's live schema and recovery evidence are recorded. Then publish the new parent/API/worker code; verify the schema preflight, API HTTP health before worker startup, red-zone endpoint, baseline Phase 6.1 identities/snapshots, scheduler ownership and provider run ledger. Week 2 production refresh and independent fact reconciliation remain a separate authorized operation.
5. If Replit cannot verify the Stage A split or a safe compatibility release, or if a recovery point cannot be verified, **do not proceed with either stage**. The remaining action is platform-specific confirmation of Publish controls/ordering, not an unsupported migration workaround.

**HOLD — NO VERIFIED SAFE DEPLOYMENT PATH**
