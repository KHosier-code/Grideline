# Stalled Odds API capture: development investigation and approval proposal

**Basis:** code inspection in development and the read-only production audit through 2026-09-25 16:18 UTC. This document is a proposal, **not** approval to change production data or issue a provider request. No Odds API call, capture replay, production write, restart, or deployment was performed for this investigation.

## What is known

- The audit records request **37** as `running` since 2026-09-25 00:14 UTC, without an event-audit row or completion. The last completed HTTP 200 request was at 00:08 UTC, with 384 duplicate observations and no new quote rows. A later intent was skipped. The next adaptive slot shown in the audit was 2026-09-26 14:00 UTC. These are **audit-time observations**, not a claim about the current live state. See [production recovery audit](gridline-production-recovery-audit.md#3-worker-and-integration-evidence).
- The persistent worker starts both `startDataScheduler()` and `startFeedScheduler()` (`worker.ts`). Odds are owned by `odds-adaptive` in `scheduler.ts`, **not** by `feed-scheduler.ts`: the latter runs injuries, nflverse and weather. The API process does not start the recurring scheduler; the production launcher starts a separate worker and API after a DB smoke check. The worker retires legacy fixed odds job rows, but retains their history.
- The scheduler claims a due job using a database row lease (two-hour TTL), writes an odds `data_sync_runs` row, then calls `captureOddsSnapshots`. On completion it advances the next occurrence and clears the lease only if its owner still matches. On worker startup, overdue occurrences are *skipped*, not caught up. Startup recovery marks old `data_sync_runs` as failed, **but does not reconcile `odds_api_requests`**. An expired lease is not proof the previous process has stopped; there is no lease renewal/fencing of the capture itself.
- `captureOddsSnapshots` creates an `odds_api_requests` intent under a database-wide admission transaction before the fetch. Scheduled intents have a unique `jobKey:scheduledFor` key. The provider fetch is one request with no retry and a 15-second abort signal. The timeout does **not** bound the complete operation: finding the provider event ID, parsing/persisting observations, updating the request, and writing audits also involve database work. An exception after the row becomes `running` but outside the fetch/error and response-decode handlers can leave it there. A worker exit, blocked DB operation, or lost DB update could do so too. **The exact failure point for request 37 is not established** by the audit or by a missing event-audit row; it does not prove the provider was or was not charged.
- Admission rejects the *same* intent forever and skips a *new* intent if the latest non-skipped request is `admitted`/`running` or is `failed` with unknown remaining credits. That protects against another paid request while 37 remains unresolved, including the next scheduled slot **provided the deployed code and ledger still have this state**. It also means continued normal slots may be skipped indefinitely. The scheduler's preliminary quota calculation reads the latest row (including skipped rows); it is not the authoritative admission guard.
- An admitted row inherits the previous request's `credits_remaining` as a **pre-call estimate**, not a provider-confirmed post-call balance. Only response headers (`x-requests-last` per call, `x-requests-used` cumulative, `x-requests-remaining`) can confirm charge and remaining quota for that call. On fetch failure without headers, charge is unknown and the ledger keeps it unknown. The health view may display a prior balance when the latest request has no header value; it must not be presented as a reconciled balance. `requestsMade` counts non-skipped *intents*, not proven HTTP completions. Expected cost is three credits for three markets in one region, but expected cost is **not** proof of actual charge. Quotes (including change-only duplicates) and event audits are different evidence from the provider quota ledger.

## Risk and decision

The system currently favors **no duplicate paid request** over freshness. Do not mark 37 `success`, fill in quota headers, delete its intent, reset its unique key, or replace its `running` state with a routine `failed` value solely to clear the block. In particular, a `failed` row retaining its inherited, non-null *pre-call* `credits_remaining` would allow a new admission even though the actual spend is unknown. Do not manually trigger a new capture, restart the worker for a catch-up, or infer remaining credits from the 00:08 request. The audit's `partial` health and withheld recommendations should remain honest until fresh complete evidence exists.

### Approval gate A: read-only reconciliation of the incident

Before any production repair, an operator should capture read-only, timestamped evidence from:

1. Request 37 and adjacent `odds_api_requests`: intent key, requested time, status, HTTP status, credits, sanitized metadata and error; all later skipped rows with `blockedByRequestId`; event-audit counts and quote insertion times. Keep the unique intent and audit history.
2. `odds-adaptive` in `scheduler_jobs`: enabled, next/last occurrence, lease owner/expiry, last result; associated `data_sync_runs` including skipped reasons. Confirm the API and worker deployment version and that only one worker owner is active. Check worker logs around 00:14 UTC for fetch timeout, process exit, database timeouts and last successful write **without logging request URLs, keys or response payloads**.
3. If available, a provider **read-only usage/balance record** (not a paid odds endpoint) covering the interval, to distinguish an admission-only row from a charged call. If unavailable, record charge and remaining quota as **unknown**. An absent event audit or no new quotes cannot establish zero cost.

Recheck the actual live state before proceeding: the September 25 audit is not a lock on future behavior. If the worker is still executing the request, isolate that process safely before changing request state; expiration alone is not a fencing signal.

### Approval gate B: bounded development fix, no live provider test

Implement and review separately before considering production:

- Introduce an explicit terminal **unresolved charge** state or equivalent reconciled flag for abandoned/expired paid intents, preserving original request ID, intent key, initial estimate, known headers and reason. Reconcile only when owner liveness is settled and a bounded end-to-end operation has failed/ended; never convert an unknown charge into a known balance. Keep unresolved-charge intents as an admission block until there is independently verified quota evidence and operator authorization for future *new* slots. Never replay the old intent.
- Cover all post-admission work with bounded, explicit failure handling and conditional request-state transitions, including the pre-fetch event lookup, response processing, DB persistence and audit write. Keep any partial quote/audit evidence attributed to the original request and distinguish “HTTP attempted” from “admitted only.” Fence stale owners so late completion cannot overwrite an operator reconciliation or a newer attempt. Ensure a timeout/cancel of a database operation actually stops/discards that operation rather than only timing out the await.
- Make the odds job's lease/worker ownership observable and consistent with paid-request finalization. A lease expiry or scheduler restart should produce a visible incident state, **not** an automatic paid retry. Distinguish admission count, confirmed HTTP count and unknown charges in health; do not display copied pre-call quota as confirmed remaining quota. Retain partial/stale consumer status until coverage is genuinely refreshed.
- Validate with simulated HTTP responses, never the live provider: crash before fetch, timeout with no headers, failure after headers, failure during quote/audit persistence, expired lease while a prior owner remains active, same-intent reentry, later distinct slot blocked by unresolved charge, and operator reconciliation followed by exactly one authorized future slot. Check credit arithmetic from per-call headers and cumulative deltas; enforce the unique intent key and no catch-up burst.

### Approval gate C: production action (separate decision)

After the fix is reviewed, obtain explicit approval for any deployment, ledger annotation, scheduler-state edit or paid request. Preserve request 37 and every skipped intent as audit evidence. If provider usage cannot confirm a safe remaining balance, leave paid capture paused and quota **unknown**; do not turn a stale balance into available credit. If it can be confirmed, record the evidence and authorize at most a *future normal* occurrence under the new admission policy, with a pre-agreed credit budget. Observe one completed request and its per-call/remaining headers, linked event audits, scheduler outcome and consumer health. If that verification fails, return to the blocked state without retrying or catch-up. No historical quote backfill, model change, or recommendation override is part of this proposal.

## Scope boundary

This investigation changes no application behavior. It establishes a likely **unbounded post-admission / unreconciled-intent gap**, not a proven root cause of the specific 00:14 incident or proof of a charge. Production evidence and any repair require a separate approval.
