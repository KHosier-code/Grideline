# Consumer production-build performance

Run `pnpm test:consumer-performance` from the workspace root (or `pnpm --filter @workspace/nfl-analytics perf:report` to report without enforcing budgets). Start the API Server workflow first. The command builds the real production app plus a **test-only HTML entry**, serves the optimized files with Vite preview, measures anonymous Home, the weekly Home component fixture, the separate account-shell fixture, and Games before looking up a real game ID from the consumer dashboard. Fresh Chromium contexts are used per route and profile. `PERF_OUTPUT=path.json` saves the machine-readable report. To check a non-root deployment path, run `BASE_PATH=/gridline/ pnpm test:consumer-performance`. The script also checks anonymous `/admin` and `/sign-in` boundaries and navigates from each route.

For **cross-release weekly Home trends**, run `PERF_API=fixture PERF_OUTPUT=home-trend.json pnpm test:consumer-performance` (or use `pnpm --filter @workspace/nfl-analytics perf:report` for a non-enforcing report). This separate mode needs **no API Server**: it measures only `/tests/performance-home.html` with a fixed six-game, chart-bearing synthetic API workload. It checks the weekly heading, card count, supported pregame comparison plot, historical trend plot, navigation, and budgets in both profiles; unexpected API requests fail the run rather than falling through to live evidence. Reports identify `apiMode` and `fixtureVersion`. Compare only runs with the **same fixtureVersion, profile, basePath and measurement environment**; save successive JSON reports externally and compare `routeReadyMs`, `lcpMs`, `jsTransferKiB`, `longTaskBlockingMs` and `interactionMs`. The fixture's far-future season and cutoff are synthetic, not a prediction or data-quality claim. Increment its version when the workload or expected chart content changes. Preserve the default live-API command for operational measurements of today's actual slate, and never compare its times directly to the fixture series.

The fixture at `/tests/performance-home.html` renders the **same `ConsumerHome` component** as the signed-in `/` route, with real dashboard and matchup requests. It has a minimal navigation shell instead of the signed-in account controls; it does not create a Clerk session, grant server permissions, mock the API, or test account-specific interactions. Its `scenario` is marked separately from anonymous production routes in the report. The performance commands first build the ordinary production app, then build the fixture **separately** and copy its files into the local preview directory. This preserves the normal app bundle and chunking for the public-route measurements; a normal `pnpm --filter @workspace/nfl-analytics build` does **not** ship the fixture. The fixture isolates weekly content load from Clerk startup, so do not compare its total JS transfer or account-shell rendering directly to a signed-in live session.

The separately labeled `/tests/performance-home.html?shell=account` scenario uses the **production consumer shell view and account-navigation component** around the real weekly Home content. It supplies an in-memory signed-in *visual state* and a local stand-in button in place of Clerk's UserButton. `accountActionMs` measures opening that stand-in (including the mobile menu on mobile); `interactionMs` measures clicking Saved games to change the fixture URL. The harness then reloads that URL into the **real anonymous** production app and checks its signed-out saved-games state; that reload is not included in `interactionMs`. It neither loads private saved games nor exercises the Save/Remove mutations, Clerk startup, UserButton profile UI, authenticated API timing, or server authorization. There is no fixture route in the ordinary production build, no token or fake user ID, and no browser-side authentication bypass. Do not report this as signed-in end-to-end performance or compare its JS transfer to a live Clerk session.

For a focused account-shell measurement after building, run `PERF_ACCOUNT_ONLY=1 node artifacts/nfl-analytics/tests/performance.mjs` from the workspace root. It still checks the anonymous admin boundary, but skips other route measurements.

In a September 2026 root-path budget run against the development API, the separately built fixture reached the `2026 · Week 3` heading in 2,750 ms (mobile) and 630 ms (desktop), with LCP of 2,736 ms and 624 ms, respectively; navigation took 53 ms and 35 ms. Both profiles passed the budget. A separate `/gridline/` report run also reached the weekly heading and followed the Games link in both profiles. These are reproducible route measurements, not a controlled comparison to the historical anonymous Home sample below; content and API timing can change between runs.

Profiles: mobile is 390×844, 2× DPR, 4× CPU slowdown, 150 ms network latency and 200 KiB/s download; desktop is 1440×900, 1× CPU, 20 ms latency and 5 MiB/s download. The local production preview has no CDN. Browser requests to `/api` are forwarded to the running development API to keep real saved evidence; this proxy forwarding is **not** subject to the emulated browser network throughput. Clerk availability and API content can vary for the anonymous routes; the fixture has no Clerk initialization. Runs are single samples, not lab percentiles or field Core Web Vitals.

Budget per route (mobile / desktop): LCP ≤9,000 / 4,000 ms; time until route heading or finished detail state ≤11,000 / 6,000 ms; click-to-URL transition ≤3,500 / 2,000 ms; CLS ≤0.1; cold-load JS transfer ≤400 KiB. The check rejects access-check/loading screens as completed pages, HTTP errors, missing links, and unauthorized admin-shell rendering. The report also records DOMContentLoaded and accumulated long-task blocking time (duration beyond 50 ms). Interaction time measures navigation response, **not** INP or data completion on the destination.

## Measurements

Captured in this workspace against the production build, with a fresh browser context per route. The historical baseline below was taken before the split; it is a diagnostic of the original access gate, **not** a valid route-level LCP or interaction comparison. The first pass measured the access-check screen because Clerk did not finish initializing on the local preview hostname. The revised router allows public pages to render during that check. The table below predates the signed-in Home fixture and reports **anonymous Home**, not the new fixture. No real signed-in session or admin page is claimed to be measured by this harness.

Before: one 1,264 KB minified JS asset (348 KB gzip). After: 612 KB entry (175 KB gzip); Recharts' 382 KB chart module (105 KB gzip) is requested on Game Detail and Performance, not on Home or Games. The cold Home JS transfer decreased from 340 KiB to 177 KiB (48%). This is evidence of less initial download, **not** proof that signed-in route time improved: the baseline did not reach those pages. The non-root `/gridline/` build and budget run passed with route headings, navigation, and boundary checks. Existing API data still determines whether projections and graded charts appear.

Optional verified imagery is refreshed in the background for consumer routes; stale verified images or null placeholders are returned immediately. The unit test in `artifacts/api-server/src/lib/verified-imagery.test.ts` holds a simulated remote refresh pending and checks that a cold read remains immediate and concurrent requests share one attempt with a five-minute retry gap. This isolates the source-timeout behavior from live GitHub variability. The browser check does not artificially purge the API process cache; for a cold-process integration reading, restart the API workflow before running the budget command. After restarting the API once and running the root-path budget command with no manual API warmup, the first dashboard request completed in 266 ms; mobile Home reached its heading in 2,405 ms with 2,364 ms LCP, while mobile Games reached its heading in 2,241 ms with 2,232 ms LCP. The separate pending-refresh unit test covers the source-timeout case, which a live GitHub request cannot reliably reproduce.
